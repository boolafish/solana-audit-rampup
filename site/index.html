Mental model deltas

The mistakes usually come from importing EVM assumptions where Solana is account-list driven.

State

No implicit contract storage

Programs are executable accounts, often with ProgramData if upgradeable. Persistent protocol/user state lives in separate accounts supplied by the transaction.

Read notes →Auth

No implicit `msg.sender`

A pubkey in the account list is not authorization. Require signer status or validated PDA signer seeds.

Read notes →CPI

External calls are explicit

Program ID and every callee account may be caller-supplied. Pin program IDs and validate CPI accounts.

Read notes →Ownership

Account owner ≠ token owner

Solana account `owner` controls data writes. SPL token authority/mint are fields inside token accounts.

Read notes →Storage

Rent and size are explicit

Rent usually means rent-exempt minimum balance and lifecycle funding/refunds, not recurring EVM-style storage rent.

Execution

Atomic tx + account locks

Transactions compose multiple instructions atomically; writable accounts lock parallel execution and can create hot-account DoS.

Account validation matrix

The single most useful Solana audit artifact: one row per account per instruction.

Protocol stateowner = program id; discriminator/type/version; PDA/address; `has_one` authority/config/pool; writable only if mutated.
Authorityhuman keypair must be `Signer`; PDA authority must have validated seeds/bump and scoped resource; relationship to state checked.
Token vaultowner = Token/Token-2022 program; mint = expected mint; authority = vault PDA; address/ATA derivation if required; extension policy checked.
CPI programprogram id pinned; executable when raw; CPI metas use already-validated accounts; signer/writable privileges minimized.
Oracle/sysvarexact feed/sysvar address; owner/program; freshness/confidence/status; decimals/exponent normalization; instruction position for introspection.

Open audit notes

Anchor-specific audit focus

  • Prefer typed accounts: Account<T>, Program<T>, Signer, InterfaceAccount<T>.
  • Treat UncheckedAccount, AccountInfo, and remaining_accounts as fully untrusted.
  • Use constraints: seeds, bump, has_one, owner, address, executable, token constraints.
  • Verify exact Anchor version for close, duplicate mutable behavior, init_if_needed, and token-interface semantics.

Full notes: docs/anchor-security.md

CTF-style questions

  • Can I pass a fake account with matching bytes?
  • Can I pass the same writable account for two roles?
  • Can I swap one valid account for another user/pool/mint?
  • Can I choose a malicious CPI target or malicious CPI accounts?
  • Can I re-run initialize, revive a closed account, or exploit rounding by splitting actions?

Full notes: docs/core-solana-security.md

State / storage / MEV caveats

Rent: usually means rent-exempt minimum balance and account lifecycle: who funds creation/realloc, whether final accounts remain rent-exempt, whether closed accounts can be reused, and who receives lamport refunds.

MEV/front-running: Solana has no globally gossiped Ethereum-style public mempool, but pending orderflow is not guaranteed private. RPCs, leaders/validators, relays/block engines, searchers, private orderflow, Jito bundles, priority fees, liquidations, and oracle updates can still create ordering risk.

Storage: there is no implicit contract storage mapping. Every state account is supplied by the transaction and must be validated for owner, type, PDA/address, signer/writable privilege, and relationship to other accounts.
