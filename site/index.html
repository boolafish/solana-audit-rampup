Mental model deltas

The mistakes usually come from importing EVM assumptions where Solana is account-list driven.

State

Code and state are separate

Programs are executable accounts. Persistent state lives in accounts supplied to each transaction; validate each one.

Auth

No implicit `msg.sender`

A pubkey in the account list is not authorization. Require signer status or validated PDA signer seeds.

CPI

External calls are explicit

Program ID and every callee account may be caller-supplied. Pin program IDs and validate CPI accounts.

Ownership

Account owner ≠ token owner

Solana account `owner` controls data writes. SPL token authority/mint are fields inside token accounts.

Storage

Rent and size are explicit

Creation, rent-exempt lamports, realloc, close, and refund recipients are part of protocol security.

Execution

Atomic tx + account locks

Transactions compose multiple instructions atomically; writable accounts lock parallel execution and can create hot-account DoS.

Anchor-specific audit focus

  • Prefer typed accounts: Account<T>, Program<T>, Signer, InterfaceAccount<T>.
  • Treat UncheckedAccount, AccountInfo, and remaining_accounts as fully untrusted.
  • Use constraints: seeds, bump, has_one, owner, address, executable, token constraints.
  • Be careful with init_if_needed, realloc, close, CPI signer seeds, and Token-2022 interfaces.

CTF-style questions

  • Can I pass a fake account with matching bytes?
  • Can I pass the same writable account for two roles?
  • Can I swap one valid account for another user/pool/mint?
  • Can I choose a malicious CPI target or malicious CPI accounts?
  • Can I re-run initialize, revive a closed account, or exploit rounding by splitting actions?

State / storage / MEV caveats

Rent: usually not a standalone exploit class; the risk appears in account lifecycle: who funds creation, whether realloc remains rent-exempt, whether closed accounts can be reused, and who receives lamport refunds.

MEV/front-running: Solana does not have an Ethereum-style public in-protocol mempool, but ordering games still exist through leaders, priority fees, private orderflow, Jito/bundles, liquidations, oracle updates, and DEX routing. “No mempool ⇒ no front-running” is not a safe audit assumption.

Storage: there is no implicit contract storage mapping. Every state account is supplied by the transaction and must be validated for owner, type, PDA/address, signer/writable privilege, and relationship to other accounts.
